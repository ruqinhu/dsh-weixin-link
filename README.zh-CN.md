# @ruqinhu/dsh-weixin-link

[English](README.md) | 中文

给 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的微信 iLink 通道：
收消息，并且**不依赖模型记得**就把回合结果投递出去。

DSH 没有内置 IM 投递。这个插件补两件事 —— `weixin_push` 工具，以及回合结束时自动投递 ——
而第二件才是设计本身。

下面按约束到来的顺序展开：第 1 节是决定一切的那一条，第 2–8 节每节一个机制、并交代促成它的
那次失败，第 9 节是实测（含一次真实故障），第 10 节是开放问题；安装与配置速查放在最后。

## 1. 决定一切的约束

iLink 每次发送都必须带 `context_token`，而**这个 token 只能从入站消息里拿到**，没有别的
办法生成。

所以一个安静的夜晚意味着 07:00 早报发不出去，直到 owner 主动发一条消息。插件不假装能绕过：
这类消息会被暂存，等真实入站消息刷新 token 后立刻重放。**故意不做保底通道** —— 静默的保底
会掩盖失败，而不是暴露失败。

```text
  入站   iLink getupdates ─► context_token ─► 分发 ─► agent（会话）
                │                              │
                │                              └─ 没有活 agent？用
                │                                 sessionController.resolveAgent() 恢复
                ▼
  出站   session/event ─► turn/end ─► policy.decide ─► dedupe ─► push ─► 收据
                                            │                     │
                                            │                     └─ 失败 ─► 暂存
                                            └─ 跳过：只写 trace          │
                                                            重放定时器 ───┘
  存活   每轮 ─► state/heartbeat.json ─► Watchdog（60 秒）─► 静默则重启循环
```

这一条约束解释了暂存队列、重放规则，以及为什么「token 过期」是一等状态而不是一个可重试的错误。

## 2. 投递是传输层的职责，不是模型的自律

最早的版本在每个定时任务的 prompt 里写一句话：「完成后必须调用 `weixin_push`」。它失败得
很安静，有三种形态：

- 模型把回复写进会话，回合正常 `completed`，用户什么也没收到 —— 从模型的角度看，在会话里
  回答是正确行为，它不知道这句话是要发到手机的。
- 模型先调 `weixin_push` 发正文，再在会话里补一句「已通过微信回复你了」。用户收到的第二句
  是元叙述，不是内容。
- 任务失败时，prompt 仍然说「必须发」，于是错误被当成报告发了出去。

根子上，投递是**传输层**的职责。现在插件订阅 DSH 的全局 `session/event` 总线，在 `turn/end`
时取该回合最后一条 `assistant/message` 的正文自己发送。DSH 的 `dsh-schedule` 在投递消息后
只等 `sessions.flush()`，它既不知道也不关心 agent 回了什么 —— 所以这件事必须由通道做。

## 3. 哪些回合会被投递，以及投几次

**3.1 来源。** 按该回合第一条 `user/message` 的 `source.kind` 判定：

| `source.kind` | 来源 | 投递 |
| --- | --- | --- |
| `schedule` | 定时任务 | ✅ |
| `weixin-link` | 用户在微信发起 | ✅ |
| `user` | 用户在终端 / Web 输入 | ❌ 人就在键盘前，同一句话在屏幕上已经有了 |
| `runtime-context` / `skill-catalog` / `time-context` | 注入的上下文 | ❌ 不是对话 |
| `compact-checkpoint` / `provider` / `fallback` | 会话压缩、标题生成 | ❌ 内部维护，投了就是噪音 |

只认**第一条** user 消息：每个回合后面都跟着注入的上下文（运行时快照、技能目录、时间上下文），
取最后一条会把所有回合都判成上下文，结果一条都不投。

**3.2 恰好一次。** 一个回合只投递一次。若模型在该回合内自己调过 `weixin_push`，自动投递让位 ——
否则同一条内容会收到两遍。插件没看见开局（`turn/start` 缺失）的回合也跳过：没有开场消息就分不清
这是要发给 owner 的报告还是会话标题生成，猜错不是骚扰手机就是丢掉真报告。

**3.3 长度。** 单条消息硬上限 **2,200 字符**，在代码里强制。iLink 对超长内容的失败不是干净的
拒绝 —— 发送可能返回 message id 却根本没送达。完整报告写进网页版，微信只发摘要，截断时追一行
说明并指向首行链接。上限不依赖模型遵守，因为投递已经不看模型了。

## 4. 沉默是一种失败，所以两头都设了边界

定时任务跑完但没输出时，发一条 `本次无产出（时间戳）`。静默会让「跑了但挂了」和「根本没跑」
无法区分，而两者该做的处置完全不同。

prompt 可以显式放弃这次通知：**整个回合正文恰好只有 `[SILENT]`** 时跳过。只按整体相等判定，
而且容忍形状 —— 被要求只输出 `[SILENT]` 的模型有时会加反引号或句号，这对人来说意思一样。
正文里提到这几个字不影响投递。

本该投递的回合如果没有以 `completed` 结束 —— 出错、被中止、被取消 —— 发送
`⚠️ 回合未完成（原因，时间戳）：本次没有可投递的内容。`，而不是它的半截正文。碎片不能发：
那是答案的一部分，不是答案。但把整个回合丢掉（这是插件最早的行为），会让 07:00 崩掉的报告
和「今天没排任务」在手机上完全一样。

这类通知每个会话每小时最多一条。陷入重试循环的任务否则会每次尝试都打扰 owner，而 owner 对此
的反应是静音整个通道 —— 正常的报告也一起被静音。已经自己调用过 `weixin_push` 的回合除外：
它已经说过要说的话了。

## 5. 第二级过滤：同一段文本不发两遍

自动投递与 outbox 重放是两个互不通气的发送方。重试已经送达的报告，可能在几分钟后被重放；
重连后被回放的回合，也可能结束两次。

所以十分钟内发过的相同文本视为已投递。十分钟比这里任何一条重试路径都长，比同一个任务的两次
运行间隔都短。成功发送只在一处登记 —— 发送路径本身 —— 于是这个窗口覆盖所有发送方，重放前
也会查它。

**5.1 为什么不用 LLM 判定。** 为每条消息调一次模型来决定「值不值得打扰 owner」，等于每次
投递都付一次往返，还引入一种新的静默出错方式：一个说「别发」的分类器和一次崩溃长得一模一样，
而这正是本插件要防的失败。

**5.2 为什么不做合并。** 把几乎同时结束的几个回合合成一条消息，是另一种显然的降噪手段，被否
的理由和 LLM 闸门一样：它推迟了价值随时间衰减的报告；它让 2,200 字符上限变得更难处理（超长
失败是静默的）；而且一批里中途失败，比重放单条暂存消息更难收拾。去重窗口只消除「同一段文本
发两遍」的噪音，不碰那些本来就不同的内容。

## 6. 收不会被发挡住

outbox 重试原先跑在长轮询循环里，而且是 `await` 的。限流退避是 30 → 60 → 120 秒，所以一条
暂存消息就意味着这个通道最多三分半钟收不到任何东西 —— 一次发送延迟变成了对话延迟。

现在重放走独立定时器（`replayIntervalMs`，默认五分钟）带单飞守卫，负责收的循环只负责入队。
开机同理：新进程先起轮询循环，暂存消息在后台重放，而不是一直聋到退避阶梯走完。

## 7. Watchdog：循环自己报不出来的那种失败

轮询循环是包在网络调用外面的 `while (true)`，它认识的每种失败都被捕获并重试。它处理不了的，
是它看不见的那种：某次请求在传输层里永久挂起，或者某个 Promise 永不 settle。这两种情况下进程
还活着，日志什么都不说，之后每一份报告都投递进了一个已经不再监听的通道。

`state/heartbeat.json` 每轮重写：上次尝试、上次成功、连续失败数、入站计数、重启次数。插件
每 60 秒判读一次，连续三个客户端预算（默认 40 秒超时下即两分钟，下限 90 秒）**没有任何轮次
被尝试**，就原地重启循环。

信号是**沉默**，不是失败：一轮失败仍然证明循环在转，而重启一个已经在退避重试的循环，会掐掉
正在进行的那次重试，下一次 tick 再掐掉下一次。一直在失败的循环不予打扰 —— 重启它也不会让
网络回来。

心跳写成文件而不是日志行，是为了让人、或者另一个进程里的外部 cron，不用 grep 就能回答
「它还活着吗」。`weixin_status` 里的 `lastPollAgeMs`、`pollRestarts`、
`consecutivePollFailures` 读的也是它。

## 8. 发送策略、暂存与重放

**8.1 发送路径。** 自动投递和 `weixin_push` 走同一条路：

1. 先试一次。
2. 分类失败：

| 类别 | 动作 | 为什么不换一种 |
| --- | --- | --- |
| token 失效 | 暂存，不重试 | 只有新的入站消息能生成 token |
| 被限流 | 退避 30/60/120 秒，之后暂存 | 退避完就丢，看起来和「从未被调度」一模一样 |
| 其他 | 立即重试一次，再失败就放弃 | 更多重试会把一次抖动变成队列停摆 |

3. 每次尝试写一行 JSONL 收据。

唯一的例外是自动投递发现**根本没有 `context_token`**（还没收到过任何入站消息）。这种情况
不暂存：把几天前的报告重放到今天比丢掉更糟。

**8.2 重放。** 重放只有一条规则，也是用事故换来的：**只有能证明永久失败的条目才删除**，
其余全部保留。早先的实现把「既不是 `NEEDS_INBOUND` 也不是 `RATE_LIMITED`」都当成永久失败
删除，而当时真实发生的失败是 `ret:-2 prepare failed`，归类为 `UNKNOWN` —— 那是**暂时性**的。
一条 12:40 午报就这样没了，收据写着 `ok:false`，而 outbox 已经空了。

被重放的条目失败时不会再暂存：它本来就在 outbox 里，再暂存一次会为同一段文本写出第二个文件，
等 token 恢复后每一份都会被发出去。

## 9. 实测

- **单测**：248 个、21 个文件 —— 判定矩阵、回合追踪、outbox 规则、去重窗口、心跳与 Watchdog
  各有自己的测试；`tsc --noEmit` 干净。
- **投递往返**：10:00:04 收到入站并刷新 token，回合 10:00:24 完成，同一秒投递成功
  （`ok msgid=7523202391886746000`）。
- **Watchdog**：心跳逐轮前进，连续运行 14 小时 `restarts: 0`；循环停摆时由同一次 tick 重启。

**9.1 一次故障，trace 是这么记的。** 配额故障期间模型返回 `429 AccountQuotaExceeded`。

```text
10:40:29Z skip session=… turn=304 reason=not-completed     ← 旧版本
10:42:31Z skip session=… turn=305 reason=not-completed
10:44:34Z skip session=… turn=306 reason=not-completed
10:46:33Z send session=… turn=307 kind=failure len=44      ← 新版本
10:46:33Z ok   session=… turn=307 msgid=7522972414050248000
```

四分钟的沉默变成手机上的一行字：这一轮没跑完。之后限流器把后续通知挡了回去 —— 同一份 trace
里记作 `skip … reason=failure-notice-rate-limited` —— 正是第 4 节描述的行为。

## 10. 开放问题

- **token 无法由插件刷新。** 如果 owner 大约十二小时没给 bot 发消息，发送会以
  `ret:-2 prepare failed` 失败并暂存，直到他再发一条。这是 iLink 的性质，不是插件能改的。
- **单轮询、单收件人。** 多账号或多收件人需要一层路由，这个插件没有。
- **重放是串行的。** 一次慢发送会拖住后面所有条目；并发重放需要按条目的锁才安全。
- **失败通知的每小时下限存在内存里**，重启会多一条。持久化它要为每次失败多写一个文件，只为
  少发一条消息。
- **没有图片、没有富卡片。** 只有文本：2200 字符上限和「静默丢包」这种失败形态，决定了文本
  是唯一失败可观测的载荷。
- **Watchdog 分不清「挂死」和「进程被暂停」。** 调试器停顿或长时间 GC 看起来都像停摆；重启
  无害，但会被记一次。
- **写入时没有任何 outbox 校验。** 坏条目在读取时被跳过并通过 logger 报告，不会被修复。

## 凭据

token 通过 DSH 凭据库读取（`ctx.credentials.resolve()`），**不直接读 `process.env`**。这是
有意的：凭据库已经按 `$DSH_HOME/.credentials.yaml` → 继承环境变量 → 项目/用户 `.env` 分层
解析，绕过去反而会遮蔽受管存储。

在 `tokenEnv`（默认 `WEIXIN_BOT_TOKEN`）指定的名字下配置凭据。

## 配置

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `tokenEnv` | `WEIXIN_BOT_TOKEN` | bot token 的凭据名 |
| `accountIdEnv` | `WEIXIN_BOT_ACCOUNT_ID` | 账号/bot id 的凭据名 |
| `baseUrl` | `https://ilinkai.weixin.qq.com` | iLink 端点 |
| `dataDir` | `~/.dsh/weixin-link` | token、outbox、收据、投递追踪目录 |
| `poll` | `true` | 是否跑入站长轮询 |
| `pollTimeoutMs` | `40000` | 客户端预算，必须大于服务端 35 秒挂起 |
| `defaultUserId` | `""` | 收件人；空表示"最近一次入站发送者" |
| `echoOwnMessages` | `false` | 是否把 bot 自己的消息当作入站 |
| `sessionId` | `""` | 入站消息投递到的会话，冷启动时自动恢复 |
| `replayIntervalMs` | `300000` | outbox 重试间隔，独立定时器 |
| `dedupeWindowMs` | `600000` | 窗口内的相同文本算已投递 |
| `notifyTurnFailures` | `true` | 是否通报未正常结束的回合 |
| `watchdogIntervalMs` | `60000` | 存活检查间隔；`0` 关闭 Watchdog |

## 工具

| 工具 | 用途 |
| --- | --- |
| `weixin_push` | 主动发送文本；发不出去时自动暂存 |
| `weixin_status` | 登录态、token 年龄、最近投递、积压深度、轮询存活 |

`weixin_push` 保留给「让 agent 现在主动发一条」的场景。日常投递不需要它 —— 插件会自己做，
而调它会让该回合的自动投递让位，避免重复。

## 收据与追踪

**收据** `dataDir/receipts/YYYY-MM-DD.jsonl`：每次发送尝试一行，按操作者的 **+08:00 本地日**
归档而非 UTC。

**投递追踪** `dataDir/delivery-trace.log`：每个回合的判定结果一行，包括**跳过**的回合和原因。

两份分开是必要的：收据只记录尝试过的发送，一个被策略跳过的回合不会留下收据。当报告没到时，
第一个问题是"到底有没有考虑过投递"，这个问题只有追踪文件能回答。

```
send session=... turn=12 kind=turn len=63
ok   session=... turn=12 msgid=7521135910923441000
skip session=... turn=13 reason=source-not-deliverable
skip session=... turn=14 reason=duplicate
watchdog-restart reason=stalled lagMs=142000 failures=0
```

## 入站投递

入站文本作为普通后续回合投给最近活跃的根 agent，来源标记为 `weixin-link`。若 profile 里没有
agent，token 缓存仍然会刷新 —— 那才是解锁投递的关键部分。

冷启动时用 `sessionController.resolveAgent()` 恢复会话，它返回裸 `Agent`、`{ agent }` 或
`{ error }` 三种形态，都要认。

> `sessionController` 必须写进 `static inject`。cordis 对未声明的服务**抛异常**而不是返回
> `undefined`，被 `try/catch` 吞掉后会表现为"消息收到了但没人回"。
